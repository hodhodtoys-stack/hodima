# انتشار هدیما (`/release`)

قانون‌های پایه در `CLAUDE.md` (قانون ۶ و «روش هر مرحله» ۴ تا ۷) است؛ این اسکیل همان‌ها را به ترتیب اجرا می‌کند و `bin/release-check.py` بررسی‌های قابل‌ماشین را انجام می‌دهد. کار فقط وقتی «تمام» است که مرحله ۹ قبول شده باشد.

با آرگومان `check`: فقط مرحله ۰ و `python3 bin/release-check.py plan` و `python3 bin/release-check.py` را اجرا کن، نتیجه را فارسی و ساده گزارش بده و چیزی عوض نکن.

## ۰. محیط و شاخه
در محیط ابری قلاب شروع جلسه (`.claude/hooks/session-start.sh`) همه را آماده کرده است؛ این‌ها فقط بررسی‌اند (اگر خلاصه شروع گفتگو خطا گفت، گزارش: `~/.cache/hodima/session-start.log`).
```bash
php -v | head -1                      # باید 8.4 باشد؛ وگرنه روش HODIMA-AUDIT.md بخش ۳۵
[ -e vendor/bin/phpcs ] || bash tools/quality/install-offline.sh   # PHPCS/PHPStan + npm ci
git fetch origin claude/hodima
git rev-parse --abbrev-ref HEAD       # باید claude/hodima باشد
git rev-list --count HEAD..origin/claude/hodima   # اگر >0: git pull --no-rebase origin claude/hodima، بعد دوباره تست
```
شاخه دیگری نساز و push نکن (حتی شاخه‌ای که محیط معرفی کرده).

## ۱. چه چیزی منتشر می‌شود؟
```bash
python3 bin/release-check.py plan
```
بسته‌های تغییرکرده (قالب و ۴ افزونه) نسبت به `origin/claude/hodima` و نسخه بعدی پیشنهادی را نشان می‌دهد.
- **هیچ بسته‌ای تغییر نکرده** (فقط ابزار، مستندات، `.claude/`): نسخه، CHANGELOG و `bin/build.sh` **لازم نیست** — از مرحله ۵ (تست‌های مربوط) و ۷ ادامه بده. `release/` نباید عوض شود.
- **بسته تغییر کرده:** همه مرحله‌ها.

## ۲. نسخه
هر بسته تغییرکرده، و فقط همان‌ها:
| بسته | جای نسخه |
|---|---|
| قالب | `hodima/style.css` سربرگ `Version:` (ثابت `hodima_VERSION` خودکار از همین) |
| Core | `plugins/hodima-core/hodima-core.php`: سربرگ ` * Version:` **و** `const HODIMA_CORE_PLUGIN_VERSION` |
| SEO / Commerce / Media | همان الگو: `HODIMA_SEO_VERSION`، `HODIMA_COMMERCE_VERSION`، `HODIMA_MEDIA_VERSION` |

- **قالب: فقط یک پله** (رقم سوم ۰–۹، بعد رقم دوم +۱ و سوم ۰؛ مثلا 2.9.8 → 2.9.9). **بعد از 2.9.9 بپرس** 3.0.0 یا 3.1.1 (کاربر «3.1.1» نوشته بود) — بدون جواب منتشر نکن.
- افزونه: رقم سوم +۱ (مثلا 1.11.0 → 1.11.1)؛ امکان تازه بزرگ: رقم دوم +۱ و سوم ۰.
- اگر قالب به امکان تازه یک افزونه نیاز دارد: کمترین نسخه در `$required` در `hodima/functions.php` (اعلان پیشخوان) را بالا ببر. اگر منطقی از قالب به افزونه رفت: مرز `hodima_theme_has_legacy_logic()` (بخش ۵۲).

## ۳. CHANGELOG.md
بالای فایل، زیر توضیح اول، یک عنوان برای همه بسته‌های این انتشار، **ارقام فارسی**:
```markdown
## ۲.۹.۹ (قالب) و ۱.۱۱.۱ (Hodima SEO)
- [hodima] **عنوان کوتاه امکان:** توضیح برای مدیر سایت — چه چیزی عوض شد و کجا (مسیر منوی پیشخوان).
- [hodima-seo] رفع شد: …
```
- برچسب‌ها: `hodima`، `hodima-core`، `hodima-seo`، `hodima-commerce`، `hodima-media` (چندتا با ویرگول)، `[همه]`. هر بسته دست‌کم یک خط — همین متن در پنجره «جزئیات» به‌روزرسانی وردپرس دیده می‌شود.
- زبان کاربر، نه برنامه‌نویس: نام تابع و مسیر فایل نیاور؛ اگر ظاهر عوض نشده بگو «ظاهر سایت همان قبلی است»؛ اگر تنظیمی لازم است بگو کجا.

## ۴. مستندات
- `HODIMA-AUDIT.md`: بخش تازه `## N. عنوان — مرحله M` **قبل از پیوست**؛ پیوست یک شماره جلو می‌رود و همیشه آخر است. محتوا: بسته و نسخه، چه و چرا، باگ‌های پیداشده، **تست** (فقط آنچه واقعا اجرا شد) و **محدودیت**. اگر موردی از بخش ۴ رفع شد: `✅ … (رفع شد — بخش N)`.
- `CLAUDE.md`: «قالب (نسخه X)» در جدول ساختار، فهرست «مراحل انجام‌شده» (`…، عنوان (N)`)، و هر قانون تازه‌ای که کار آورده.
- `README.md` اگر امکانات یا منوها عوض شد.

## ۵. تست — قبل از ساخت
همیشه: `bash bin/lint.sh` → باید «همه بررسی‌ها قبول» بدهد (خطای جدید را با `--update-baseline` پنهان نکن).

بسته به نوع تغییر (هر کدام که صدق می‌کند):
| تغییر | دستور |
|---|---|
| هر PHP که خروجی صفحه یا اسکیما را عوض می‌کند | `tools/wp-harness/compare-with-ref.sh` (هر `LOST` باید عمدی باشد) و `tools/wp-harness/ci-check.sh` |
| CSS قالب | `tools/wp-harness/css-equiv.sh` و `tools/wp-harness/visual-compare.sh` (فروشگاه: `--wc`) |
| JS/HTML قالب | `tools/wp-harness/visual-compare.sh` |
| صفحه پیشخوان | `tools/wp-harness/admin-check.sh . /tmp/adm [slug…]` |
| تعریف تابع/کلاس سطح بالا یا ترتیب لود | بعد از مرحله ۶: `tools/wp-harness/zip-install-check.sh` (هر دو ترتیب فعال‌سازی) |
| فقط ابزار/مستندات | اجرای واقعی همان ابزار روی یک نمونه |

هر تفاوت باید عمدی و در گزارش باشد؛ چیزی را «تست‌شده» ننویس مگر اجرا شده باشد.

## ۶. ساخت (فقط اگر بسته‌ای تغییر کرده)
```bash
bash bin/build.sh        # dist/*.zip + release/ (ZIP فقط اگر محتوا فرق کند؛ JSON زمانش را فقط با تغییر واقعی عوض می‌کند)
python3 tools/eol.py     # پایان خطوط فایل‌های تغییرکرده
git diff --stat          # با اندازه واقعی تغییر هم‌خوان؟ فایل release بسته‌ای که تغییر نکرده نباید باشد
```
اگر `css-equiv` داخل build رد شد، ZIP قالب ساخته نمی‌شود: علت را رفع کن، تا ساخت قبول نشده جلو نرو.

## ۷. بررسی نهایی و commit
```bash
python3 tools/eol.py
python3 bin/release-check.py     # باید «همه بررسی‌ها قبول» بدهد؛ هشدارها را بخوان و تصمیم بگیر
git status --short               # فایل تازه‌ای جا نماند؛ dist/ و vendor/ در git نیستند
git add <فایل‌های مشخص>          # git add -A فقط اگر git status همه را دیدی
```
پیام commit **انگلیسی**:
```
Theme 2.9.9: <خلاصه>            ← یا «SEO 1.11.1: …»، «Theme 2.9.9, Core 1.2.1: …»، بدون بسته: «Tools: …» / «Docs: …»

- چه و چرا (هر بند یک تغییر؛ باگ قبلی اگر بود)

Tests: <چه اجرا شد و نتیجه، مثلا lint clean; 25 pages identical; schema unchanged; ZIP install OK>
```
و در پایان، خطوط attribution که system-reminder همین گفتگو می‌دهد (Co-Authored-By و Claude-Session). نام مدل را در پیام commit ننویس.

## ۸. push
```bash
git push origin claude/hodima
```
- خطای شبکه: تا ۴ بار با فاصله ۲، ۴، ۸، ۱۶ ثانیه.
- **رد شد (تغییر هم‌زمان):** `git pull --no-rebase origin claude/hodima`. تداخل در `release/*.zip|json` را دستی حل نکن: نسخه گیت‌هاب را بگیر (`git checkout --theirs release/…`) و دوباره `bash bin/build.sh`. تداخل در نسخه: نسخه هر دو طرف را ببین — اگر طرف دیگر همان شماره را منتشر کرده، یک پله دیگر بالا ببر و CHANGELOG را درست کن. بعد مرحله ۵ تا ۷ دوباره، سپس push.
- **403 / دسترسی:** شاخه دیگری نساز؛ دلیل دقیق را به کاربر بگو و راهنمایی بخواه.

## ۹. بعد از push
```bash
python3 bin/release-check.py post   # HEAD = گیت‌هاب، چیزی commit‌نشده نمانده، release/*.json گیت‌هاب = محلی
git status -sb                      # نباید ahead باشد
```
بررسی خودکار گیت‌هاب (`.github/workflows/quality.yml`، چند دقیقه طول می‌کشد): با ابزار GitHub MCP (`actions_list` روی مخزن `hodhodtoys-stack/hodima`، اجرای همین commit) وضعیت را ببین؛ با `sleep` منتظر نمان.
- قرمز: `get_job_logs`، علت را رفع کن و دور تازه انتشار (اگر کد بسته عوض شد، نسخه یک پله دیگر — سایت‌ها نسخه قبلی را دیده‌اند).
- هنوز در حال اجرا: در گزارش بگو و لینک بده.

## ۱۰. گزارش به کاربر (فارسی، ساده)
- **چه شد** (چند خط، زبان غیربرنامه‌نویس) و **نسخه‌ها** (مثلا قالب ۲.۹.۹).
- **مشکلات پیداشده** در کار، اگر بود.
- **تست:** چه اجرا شد و نتیجه؛ محدودیت‌ها صریح.
- **لینک commit:** `https://github.com/hodhodtoys-stack/hodima/commit/<sha>` و وضعیت بررسی خودکار.
- **کار کاربر:** اگر بسته‌ای منتشر شد: «پیشخوان ← به‌روزرسانی‌ها» (یا «بررسی برای به‌روزرسانی» زیر افزونه؛ بررسی خودکار هر ۱۲ ساعت)، بعد پاک کردن کش لایت‌اسپید؛ هر تنظیم تازه‌ای که باید روشن کند. بدون بسته: «کاری لازم نیست».
